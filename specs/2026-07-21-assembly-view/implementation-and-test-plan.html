1. Implementation stance

Implement an independent Python assembly layer and a language-neutral list codec. The Python layer owns public contracts, expiration, complete-object validation, scheduling, and dispatch. Object segments use an injected existing StorageClient; service segments use a separate ServiceSegmentFetcher SPI implemented by the user. The initial core release requires no built-in HTTP adapter. Existing StorageClient and StorageProvider behavior is not modified.
Extension boundary AssemblyPlanProvider

Injected Python SPI returns one complete object plan for a fixed descriptor generation; it need not use the portable list artifact.

Execution boundary StorageClient + Service Fetcher

Object bytes use public MSC APIs; service bytes use an independent fetch SPI.

Transport boundary User-owned adapter

HTTP, gRPC, an SDK, or a local call remains behind the user implementation of the service SPI.

Constraints inherited from the high-level design

  • No AssembledStorageProvider, Provider-to-Provider ownership, or access to a client's private provider.
  • No StorageClient subclass and no implicit registration in storage profiles, provider factories, or URI routing.
  • No MSC-defined HTTP/gRPC contract for the plan service; only the in-process provider SPI is standardized.
  • No plan-supplied credentials, unrestricted origins, storage profiles, or arbitrary executable callbacks. Any future opaque service locator remains subject to local fetcher policy.
  • Every descriptor and portable-list batch set has a mandatory expiration. V1 validates expiration and exact lengths; source selectors, validators, revisions, and checksums are deferred.
  • A read, materialization, or open-reader lifetime may cross expiration only if admitted while the descriptor was valid. New operations on that view fail until the caller explicitly resolves a new view.
  • Object, service, and inline segments remain an explicit public discriminated union; service transport adapters remain application-owned behind the public fetcher SPI.
  • The initial public façade is synchronous, read-only, explicit, and importable from multistorageclient.assembly; the execution engine must still overlap independent I/O under bounded concurrency.
  • assembly-plan/v1 always denotes exact final bytes. Format-specific semantic projection is outside v1 and cannot be activated by an optional annotation.

Requirement alignment and proposal boundaries

Explicitly required

Configured sources and services; direct StorageClient reads for object segments; transport-neutral service segments; optional source versions/validators; bounded execution; and no breaking changes to existing providers.

Defensive design, not a requirement

Requirements do not explicitly require binding_revision or resource_validator. V1 keeps ObjectSourceBinding client-only, disables logical-byte caching, and adds no public provider-specific resource-policy hook.

Explicit non-goals

V1 defines no built-in service fetcher, external service API, or format-specific projection handler. Applications supply service integrations behind ServiceSegmentFetcher.

This document records the approved v1 architectural direction. Public SPI or schema changes still receive normal API review during implementation, while private safety constants are verified by focused tests and benchmarks. Concrete transport adapters are outside this specification.

3. Runtime flow from public entry point to bytes

The complete call path for view = assembly.resolve(reference) followed by view.read(ByteRange(28672, 20480)) is:

Resolve the reference AssemblyClient.resolve canonicalizes the reference, checks client state, and rejects request limits before any provider, StorageClient, or service-fetcher call.
Acquire one complete object plan The client calls AssemblyPlanProvider.get_plan(request) once. The response contains a metadata-only AssemblyDescriptor—reference, generation, size, expiration, and optional descriptive fields—plus all ordered segments for that generation. A provider may page its backend internally, but it cannot substitute the requested reference or return a range-specific fragment. The client rejects a missing, malformed, or expired expires_at. No view is observable yet.
Validate and publish the view The validator checks exact v1 result semantics, the segment discriminator, checked global length, hard inline limits, and aliases. It then snapshots JSON inputs and freezes the resolved local source/service objects. Only now does AssemblyClient.resolve return an executable AssemblyView containing the descriptor, validated complete plan, frozen bindings, and lifecycle state. Another resolve call repeats this pipeline and returns another view.
Intersect the caller range Only after global validation, the planner intersects the requested range with object and inline segments and chooses subrange or whole-result execution for each service segment.
Dispatch bounded operations Object segments call existing StorageClient APIs directly. Range-capable services receive stable subranges. Each touched WHOLE_RESULT segment gets one core fetch call per view operation and is staged under fixed memory/temp-file bounds before slicing. Any private retry remains opaque fetcher behavior.
Verify every chunk Object bindings return exact requested ranges through StorageClient. Service fetchers advertise only their supported range modes and must return the exact required length. Stronger source identity and fetcher-internal retry policy remain application concerns.
Commit atomically Verified chunks scatter incrementally into a private destination buffer; only after every chunk passes may the execution engine return immutable bytes. V1 publishes no logical-byte cache entry.

Failure boundary

A terminal error cancels queued work, signals the shared cancellation token, closes open service result streams, discards every unpublished chunk and staged output, and returns one stable domain exception. The token is internal in v1: MSC signals it after a sibling failure or parent-client close; the synchronous public façade has no caller-supplied cancellation input. The absolute operation deadline strictly bounds admission and MSC-owned waits. A provider or service fetcher receives that deadline and must honor it cooperatively. The current synchronous StorageClient.read accepts neither a deadline nor a cancellation token, so MSC can check the deadline before and after the call but cannot preempt an in-progress read. Applications must configure the StorageClient's underlying transport timeouts and retry envelope accordingly; a late result is discarded after the deadline is observed. A future additive object-binding contract may offer stronger cancellation without changing StorageClient.

Expiration is an admission check, not an in-flight cancellation deadline. An operation admitted while the descriptor is valid may finish after expires_at. Its result may be published to the caller or atomically materialized, but a new operation cannot start on that view after expiration. A completed materialized file has an independent, application-owned retention lifetime and does not become invalid merely because its source descriptor later expires.

4. Concrete MVP contracts and models

Public models live in Python and use small frozen slotted dataclasses for their top-level fields. Nested JSON inputs stay ordinary mappings and lists for usability; they are validated and copied into a private immutable execution representation at the trust boundary. assembly-list/v1 is a normative, versioned, language-neutral JSON representation, and providers may construct the equivalent public models directly.

Descriptor is not view. AssemblyDescriptor is immutable control-plane metadata and has no byte-I/O methods. AssemblyView is the executable handle created only after MSC retrieves and validates the complete AssemblyPlan, freezes local bindings, and initializes lifecycle state. AssemblyView.metadata returns the exact descriptor captured by that view.
V1 result semantics are exact and permanent. assembly-plan/v1 always describes the caller's complete final logical bytes. Optional application annotations are informational and cannot require a format-specific projection step. Any future carrier-plus-projection contract uses a new plan version and a separate format-aware façade; a v1 client must reject it rather than silently materialize a superset.

API and protocol evolution rules

  • Unknown list/plan versions, segment kinds, and fields are rejected before binding or byte I/O. Supporting a future version never changes the interpretation of a valid v1 artifact.
  • Published provider and fetcher ABCs never gain a required abstract method within v1. Optional behavior uses a concrete default method or a new versioned SPI.
  • New façade parameters are keyword-only and carry backward-compatible defaults. New serialized model semantics require a new versioned type.
  • A future format-aware projection façade is additive and separate from AssemblyView; existing callers continue to receive the exact bytes defined by v1.
MVP configuration rule. Users configure only concurrency and operation timeout. Size, nesting, inline-data, buffering, and staging safeguards are private module constants. Changing one is an implementation review, not an expansion of the public API.

Language-neutral assembly-list batches

An assembly list is one or more ordered AssemblyListBatch values with one list_id, mandatory expires_at, contiguous zero-based indexes, and exactly the declared batch count. An object definition cannot be split between batches. The artifact exists so another process or language can exchange many named object definitions without requiring MSC to define the producer's service API. It is not a pagination, listing, or glob contract.

The codec accepts strict UTF-8 JSON, rejects duplicate or unknown fields and non-finite numbers, uses RFC 3339 UTC timestamps, and represents inline bytes as unpadded base64url. Internal constants bound encoded bytes, nesting, object count, and segment count before allocation. No public decode-limit classes or per-call limit arguments are exposed.

Invariants not expressed by the type declarations

  • Every AssemblyReference is unique within one complete list snapshot, including across batch boundaries.
  • A zero-size object has an empty plan. Otherwise, every segment length is positive and the checked sum of ordered segment lengths equals the descriptor size.
  • ObjectSegment.byte_range.size == ObjectSegment.length; InlineSegment.length == len(InlineSegment.data).
  • AssemblyDescriptor.etag, when present, is descriptive metadata supplied by the provider; MSC does not derive or enforce it in v1.
  • Operation deadlines are runtime-only values and never appear in the portable artifact.

Local binding authority and hard inline limits

Object source and service aliases are local. A list cannot choose a profile, client, unrestricted endpoint, credentials, or fetcher implementation. Validation resolves each alias and freezes the concrete local object in the view. An object resource is interpreted only through the bound StorageClient's existing public logical-path semantics; it cannot reconfigure that client or select authority outside it. Applications must therefore bind a least-privilege logical namespace appropriate for every plan they accept. V1 adds no provider-specific narrower-path policy on top of that public StorageClient namespace. Rebinding an alias never mutates an existing view. Inline data is decoded under two immutable v1 upper ceilings: at most 16 KiB per InlineSegment and 64 KiB total decoded inline bytes per object/plan. Encoded-size and overall-plan limits apply in addition; inline bytes never become a bulk-data escape hatch.

5. AssemblyPlanProvider adapter and conformance boundary

The provider is a narrow in-process SPI. It may internally call any service or local catalog, but MSC never sees its transport. Implementations translate backend responses to canonical models and backend failures to stable assembly exceptions. 

class AssemblyPlanProvider(ABC):
    @abstractmethod
    def get_plan(
        self,
        request: ResolveAssemblyRequest,
    ) -> AssemblyPlan:
        """Return descriptor metadata and every ordered segment."""

class StaticAssemblyListProvider(AssemblyPlanProvider):
    @classmethod
    def from_batches(
        cls,
        batches: Iterable[AssemblyListBatch],
    ) -> "StaticAssemblyListProvider": ...

Contract choices

  • get_plan(request) is the single required provider call. It returns a metadata-only AssemblyDescriptor inside one complete exact-result plan and never returns an executable object or a range-specific fragment. AssemblyClient.resolve validates the response, freezes local bindings, and returns no AssemblyView until both steps succeed.
  • There is no public provider or client refresh method and no automatic generation fall-forward in v1. Another resolve(reference) repeats the same single-call pipeline and returns a distinct view. A future automatic policy would be additive and must never start work from a hard-expired plan.
  • get_plan returns one complete object plan. Backend/list batching is an implementation detail; a partial segment page never enters the validator or executor.
  • StaticAssemblyListProvider.from_batches() is the bounded in-memory reference implementation. For each object definition it sets descriptor.generation = list_id and descriptor.expires_at = expires_at; reference, size, ETag, content type, and publication time come from that object definition. It constructs an exact-result assembly-plan/v1. Private hard limits are applied before committing the in-memory index. Deployments requiring disk-backed or remote lookup implement AssemblyPlanProvider directly.
  • Provider authors are not required to make get_plan thread-safe. AssemblyClient serializes calls to the injected provider.
  • The provider, public façade, and ServiceSegmentFetcher.fetch() contracts are synchronous and match the current StorageClient style. Internally, Assembly overlaps independent source/fetcher I/O through bounded concurrency; v1 adds no public async SPI and implies no Rust implementation.
  • Provider retries are internal and bounded. AssemblyClient does not layer general retries around provider calls.
  • Expiration is a hard admission check. A caller obtains a replacement through another resolve call; failure leaves the old view unchanged and an expired or closed view remains unusable.

6. Validation and range planning

Configuration validation

AssemblyClient validates max_concurrency as a positive non-bool integer and timeout_seconds as a positive finite number before dependency or network I/O. All remaining limits are private constants validated by module tests. Temporary staging uses a private file in the platform temporary directory; v1 exposes no staging-path or memory-budget configuration surface.

Validation order

  1. Validate reference, schema/list versions, mandatory expires_at, and private hard limits. Require descriptor.reference == request.reference and, when request.generation is non-None, descriptor.generation == request.generation; reject a silent fall-forward before plan/source I/O.
  2. At plan or view-operation admission, compare one captured UTC clock value with expires_at; equality is expired. Reject a newly returned plan or existing view before binding or source/service byte I/O. Every explicit later resolve(reference) calls the provider once to obtain a new view, which may represent a replacement generation.
  3. Validate that the complete plan echoes the descriptor, then perform cheap structural checks: exact model types, segment count, discriminator, strict integers, text and JSON bounds, and inline decoded limits. Reject immediately on the first violation.
  4. Tuple order is logical order. Validate every positive length/object range with checked arithmetic; compute the checked sum of every segment length and require it to equal descriptor.size, including for a partial caller read.
  5. Estimate the plan's validated encoded size with a capped serializer. Do not construct a second complete encoding; abort when the private plan-byte limit would be exceeded.
  6. Resolve object aliases to existing StorageClients and service aliases to ServiceSegmentFetchers, then freeze those concrete local objects in the returned view.
  7. Validate each service segment's requested range mode against its selected fetcher's range_modes and ensure any WHOLE_RESULT stage fits the private hard limit.
  8. Normalize and bounds-check the caller's half-open logical range, intersect it with the already validated full plan, then allocate or stage output and begin I/O.

Range arithmetic

logical interval = [offset, offset + size)  ·  segment-local interval = [intersection start, intersection end)

Python checks every canonical integer and addition against the interoperable 2**53 - 1 ceiling before allocation or dispatch. A zero-length logical read returns b"" without segment I/O, but plan validation still occurs when required to prove the descriptor's complete-object definition and global length. A user fetcher owns any conversion to its transport's range convention.

No cross-segment coalescing in v1

Every intersected object segment remains one independent logical object operation. Within it, MSC issues consecutive public StorageClient.read calls no larger than the private object chunk limit; each segment fetches only the caller intersection and copies that complete fetch. V1 never combines adjacent object segments, even when alias/resource/ranges appear compatible, because ObjectSourceBinding exposes no explicit cross-segment coalescing contract. Inline slices copy directly; STABLE_SUBRANGES receives exact intersections; each WHOLE_RESULT segment is identified by its ordinal in the current view and is staged once per admitted operation. Repeated intersections with one ordinal reuse that stage, while equal-valued segments at different ordinals never deduplicate. A future additive binding contract may enable coalescing with its own conformance tests.

7. Object bindings and ServiceSegmentFetcher SPI

The complete v1 public object-binding surface is ObjectSourceBinding(client=storage_client). The binding selects an already configured public StorageClient logical namespace; it adds no profile, endpoint, credential, provider, ownership, or provider-specific path-policy controls.

The complete service SPI is range_modes plus fetch. Assembly captures the immutable range-mode set during construction and serializes calls to each fetcher instance. Fetchers and their lifecycle remain application-owned.

The core release expects a user-owned implementation such as MyServiceFetcher. It translates one ServiceFetchRequest into the user's HTTP, gRPC, SDK, or local-service call. It never receives an AssemblyPlan, never decides segment ordering, and returns only the byte stream for one service segment while honoring declared length/range mode, the shared deadline, and cooperative cancellation. MSC standardizes this in-process SPI, not the user's external wire contract.
One request means one independently executable segment. V1 has no multi-range service batch call and assumes no sticky session or hidden ordering state. The client overlaps independent fetches under bounded concurrency and relies on the application transport for connection pooling or multiplexing. The service operation and parameters are interpreted and confined by the locally selected fetcher; plans never supply credentials. Any future locator requires a separate versioned design and the same local-policy boundary.

Frozen binding registries

  • AssemblyClient defensively copies separate object_sources: Mapping[str, ObjectSourceBinding] and service_fetchers: Mapping[str, ServiceSegmentFetcher]; malformed or duplicate aliases fail construction. Either mapping may be empty when the resolved plan uses none of that segment kind.
  • Plans select only aliases. They cannot construct a client/fetcher or mutate endpoint, profile, prefix, credentials, or retry policy.
  • The complete public object binding is ObjectSourceBinding(client=storage_client). MSC freezes that concrete association in each view. The plan's resource is a logical path inside that client's already configured public namespace; it cannot reconfigure or expand the client authority. Applications bind a least-privilege namespace suitable for every accepted plan. V1 adds no provider-specific narrower path policy.
  • StorageClients are always borrowed and never closed by AssemblyClient. Independent object reads may overlap under the client-wide concurrency and byte budgets; Assembly adds no per-StorageClient serialization policy.
  • range_modes is immutable for the injected fetcher's lifetime. Calls to the same fetcher object are always serialized across aliases and views; different fetchers may overlap under the client-wide concurrency limit.
  • The same client or fetcher may appear under multiple aliases; alias reuse does not change dependency ownership.
  • The plan provider, service fetchers, and StorageClients are borrowed. The application creates, owns, and closes them through their own public APIs.
  • On failure AssemblyClient signals the shared cancellation token, cancels queued work, closes service streams, and attempts cleanup of every MSC-owned private stage. A user fetcher observes that token through SourceReadContext; custom blocking I/O remains cooperative and must obey the context deadline.
  • Every yielded item is non-empty bytes no larger than SourceReadContext.max_chunk_bytes, which comes from a private module constant. Wrong type, empty, or oversized chunks attempt stream close and raise ServiceProtocolError before copy or staging.
  • Documented service-domain errors preserve their stable type and safe fields. Other fetcher exceptions become a redacted ServiceFetchError containing only a validated cause classification; private exception messages and transport details are never exposed.
  • A primary execution error takes precedence over cleanup failures. If execution otherwise succeeds but required stream or stage cleanup fails, discard the private output and raise the appropriate redacted service or staging error.

Service range, staging, and stability

  • STABLE_SUBRANGES is allowed only when both the segment and fetcher explicitly support it. Every requested subrange must belong to one stable logical byte string for the duration of the operation.
  • WHOLE_RESULT is the default. Within one view operation, MSC makes one core fetch() call for each touched segment ordinal, stages the full declared result, checks its length, and slices locally. Different ordinals remain distinct.
  • A WHOLE_RESULT declaration above the private per-result hard cap fails before I/O. Smaller results stage in bounded memory or a private temporary file and are never reused across view operations.
  • Exact-length mismatch raises ServiceLengthMismatchError. The current call publishes nothing and attempts cleanup of every MSC-owned stage resource.
  • Private-stage allocation, I/O, or cleanup failures use a redacted AssemblyStagingError. A primary execution error takes precedence; if execution otherwise succeeds but required cleanup fails, discard private output and report the staging error. The contract requires complete cleanup attempts but does not expose their internal ordering.
  • Destination failures use the redacted AssemblyMaterializationError(phase=..., cause_type=..., committed=...) contract. Before the atomic commit point committed=False and the prior or concurrently created destination is preserved; cleanup failure after publication reports committed=True and never falsely claims rollback.
  • Assembly adds no outer retry. Any retry hidden inside a user fetcher remains that implementation's responsibility and must stay within the supplied deadline.

8. Executor, AssemblyView, forward reader, and materialization

Client-wide admission

  • One client-wide semaphore with max_concurrency permits bounds active object and service calls across every view and reader.
  • Every top-level operation receives one absolute deadline derived from timeout_seconds; provider and service adapters receive the remaining budget.
  • Calls to the provider and to each individual fetcher instance are serialized internally. Different StorageClients and different fetchers may overlap under the global semaphore.
  • Private hard limits reject an oversized read, plan, inline payload, batch, or WHOLE_RESULT stage before its large allocation or I/O begins.

Executor algorithm

  1. Receive one fully validated complete object plan plus the caller's requested range; expiration has already passed the operation-admission check.
  2. Create one SourceReadContext with the operation's absolute monotonic deadline and thread-safe internal cancellation token. MSC signals that token after a sibling failure or parent close; v1 has no caller-supplied cancellation input.
  3. Allocate one private pre-sized output buffer after all size/coverage limits pass.
  4. Intersect the range with the three segment kinds; group object operations by StorageClient binding, service operations by fetcher, and copy inline slices locally.
  5. Acquire a client-wide concurrency budget shared across concurrent views and reads.
  6. Object operations use exact StorageClient ranges and private chunking. Stable-subrange services receive the exact requested subrange; whole-result services stage once for the touched segment ordinal and slice locally.
  7. Verify every object result, service stream, and assembled destination slice against its declared length before publication.
  8. On first terminal error, stop scheduling, signal cancellation, close open service streams, clean private stages, discard the private output, and preserve the original typed error.
  9. After every destination slice succeeds, freeze to bytes and return; v1 commits no logical-byte cache entry.

The AssemblyClient semaphore is client-wide and bounds active StorageClient and service executions; a streaming service result retains its permit and any per-fetcher lock until staging completes or closes. Creating a per-read pool would allow concurrent callers × max_concurrency active executions. A user-owned fetcher may impose a stricter transport-specific limit, but that implementation detail neither replaces nor multiplies the AssemblyClient budget.

AssemblyView and reader state

  • An AssemblyView is the executable handle. It retains one metadata-only AssemblyDescriptor, the complete exact-result validated AssemblyPlan, frozen concrete source/service bindings, mandatory expiration, and lifecycle state. AssemblyView.metadata returns that exact descriptor. None of this executable state is exposed before get_plan(request) returns and complete-plan validation succeeds.
  • It never mutates or replaces its own generation. Another AssemblyClient.resolve(reference) returns a distinct view with its own generation and expiration. V1 performs no automatic re-resolution; an expired view rejects new work before I/O.
  • Each public read, materialize, and open admission captures the clock once and rejects an expired view before range planning or source/service work. Once admitted, that operation may finish after expiration.
  • Concurrent view.read calls are supported; an individual forward reader is not thread-safe.
  • An AssemblyReader is one admitted operation from successful open until close. It owns the fixed descriptor/validated plan, SourceReadContext, operation-local complete-segment stage registry, cursor, and closed state.
  • Closing the originating AssemblyView rejects new work through that view but does not cancel an already opened reader. The reader survives independently until its own close or parent-client close.
  • Reader read calls do not recheck descriptor expiration or resolve another generation. A reader opened while valid may continue after expiration; a new open on that view fails.
  • The reader is always forward-only: seekable() returns False, seek() is unsupported by RawIOBase, and tell() reports only the current forward cursor. Use view.read(range) for random access.
  • A WHOLE_RESULT stage is created at most once while the reader traverses that segment, then released after the cursor passes it. V1 retains no stage for backward replay.
  • Using a view or reader after parent close raises AssemblyClosedError.
  • After non-negative checked validation, explicit ByteRange reads clamp at EOF: zero size or offset at/past EOF returns empty, and a crossing range ends at object size. Negative or overflowing input raises InvalidAssemblyRangeError. The clamped output length must not exceed the private read limit.
  • Atomicity is per reader call, not the reader lifetime. read/readinto stages the current call privately; terminal execution failure publishes nothing for that call, leaves cursor and destination buffer unchanged, closes the reader, and raises the typed error. Prior successful calls remain an observable prefix.
  • Override RawIOBase.read(size=-1) and readall(); compute the full clamped public-call length first, reject it above the private read limit, and advance the cursor exactly once after complete success.

Materialization

view.materialize(
    destination: str | os.PathLike[str],
    *,
    overwrite: bool = False,
) -> None

For a filesystem path, write and close a unique temporary file in the destination directory and validate the entire assembled output. Create every private materialization or complete-segment stage file exclusively, use no-follow creation where the platform supports it, and use POSIX mode 0600. Never reuse or follow an existing path. Publication retains the temporary inode's effective mode. The commit point is one atomic filesystem operation: os.replace when overwrite=True; when false, create the destination with an atomic same-filesystem no-replace primitive (initially hard-link the closed staging inode, then unlink its temporary name). A precheck is only an optimization and never supplies race safety. If no atomic no-replace primitive is supported, fail with AssemblyMaterializationError(phase="commit", cause_type="OSError", committed=False) without changing the destination. A destination created concurrently wins and is preserved. An arbitrary binary stream cannot provide atomic replace; v1 should therefore keep path materialization as the guaranteed API and direct stream users to open(). If materialization began before descriptor expiration it may complete afterward. Before the atomic commit point, any error has committed=False, removes the staging name best-effort, and preserves the previous destination. After commit, the new destination is already visible; any cleanup failure is reported with phase="cleanup" and committed=True, so MSC never falsely claims rollback. Once commit succeeds, the file's retention and deletion are application policy: later descriptor expiration neither deletes nor invalidates completed bytes. All windows of one materialization share one operation context and complete-segment stage registry, so a WHOLE_RESULT service segment ordinal is not re-executed. Every operation-local private stage is cleaned successfully before the destination commit; a cleanup failure therefore prevents publication. Each logical window is exactly min(MATERIALIZATION_WINDOW_BYTES, remaining_bytes); the last may be shorter, and the window size is a private module constant.

Memory policy

  • read is bounded by a private hard limit. The initial Python implementation may hold its mutable private output and immutable returned bytes simultaneously.
  • materialize uses windowed reads and a staging file so object size is not duplicated in memory.
  • Complete plans are bounded by segment count and encoded size before range intersection or read scheduling.
  • WHOLE_RESULT service stages have a private per-result hard cap and use bounded memory or a private temporary file; each segment ordinal is staged at most once per top-level operation.
  • Inline data has hard decoded upper ceilings of 16 KiB per segment and 64 KiB per complete object.
  • Every user-owned service stream is measured against declared length and client staging ceilings; transport metadata is never trusted as a substitute.

10. Retry, lifecycle, telemetry, and security

State retention

  • V1 has no cross-resolve() descriptor, plan, or logical-byte cache. Every resolve calls the provider once and returns a distinct view.
  • Each view retains only its own validated plan and frozen bindings until the view and its readers are closed.
  • WHOLE_RESULT staging is private to one view operation or reader and is released when that owner closes.
  • A completed materialized file is application-owned and remains independent of descriptor expiration.

Retry ownership

  • Provider adapter retries its own transport without changing the exact request.
  • StorageClient retains its documented retry behavior; AssemblyClient adds no outer object-read retry. Because the current read API accepts no deadline, applications configure its underlying transport timeout and retry envelope with the Assembly operation budget in mind.
  • The assembly executor never retries an object or service submission. It owns concurrency, internal cancellation, staging cleanup, atomic publication, and deadline enforcement for admission and MSC-owned waits.
  • A user fetcher may retry internally as an opaque implementation detail, but MSC invokes its core fetch() method once and passes one absolute deadline.
  • No layer retries invalid or expired plans, binding mismatches, unknown kinds, length mismatches, or protocol violations.
  • AssemblyTimeoutError (also TimeoutError) is the sole public outcome once the shared absolute deadline is observed exhausted at provider, scheduling, object, service, or staging boundaries. The deadline hard-bounds admission, MSC-owned waits, and cooperative provider/service work. An in-progress synchronous StorageClient call cannot be preempted and may return after that instant; MSC checks immediately afterward, discards late bytes/errors, and then raises AssemblyTimeoutError. While budget remains, a provider-local transient timeout maps to AssemblyProviderRetryableError, and object/service local timeouts map to their transport classes. The v1 façade has no caller-cancellation argument: its internal token is signaled by sibling failure or parent close, and cooperative code checks it between attempts or chunks.

Lifecycle and ownership

  • AssemblyClient borrows the plan provider, service fetchers, and StorageClients. The application remains responsible for closing those dependencies through their own public APIs.
  • Client close rejects new work, cancels queued operations, signals active cooperative work, closes MSC-owned readers, streams, and private stages, and waits for already-running synchronous StorageClient calls under their configured transport timeouts.
  • Close is idempotent. MSC attempts cleanup of every resource it owns; a cleanup failure uses the relevant redacted service or staging error and does not transfer ownership of application-supplied dependencies.
  • Live clients/views/readers are non-pickleable by default; only explicit configuration/factory wrappers may reconstruct them.
  • Expiration does not close an in-flight operation or a successfully materialized file. It rejects subsequent operations on that view.

  • Spans: assembly.resolve, assembly.plan, assembly.read, assembly.object.read, assembly.service.fetch, and assembly.materialize.

  • No logical keys, resources, credentials, or ETags as metric labels. Trace attributes are redacted and bounded.

Security controls

  • Treat provider output as untrusted and validate before allocation or I/O.
  • Limit list batch/object count, logical object size, one read, segment count, encoded bytes, decoded inline bytes, resource/parameter length, WHOLE_RESULT staging bytes, concurrency, and time.
  • Use separate local object/service aliases and frozen local binding objects; cross-operation logical-byte caching is disabled in v1.
  • Interpret object resources only through each least-privilege bound StorageClient's public logical namespace. Service fetchers confine operations to their locally configured authority; transport-specific controls belong to that implementation.
  • Create every MSC-owned private stage/materialization file exclusively, use no-follow creation where supported, and use POSIX mode 0600; publication retains that inode's effective mode.
  • Make all errors/reprs safe by construction and test redaction with canary secrets.
